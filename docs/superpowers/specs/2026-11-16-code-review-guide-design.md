# 프로젝트별 AI 코드 리뷰 체계 구축 가이드 설계

> 구현 중 승인된 변경(2026-11-16): 사용자가 private 보호 기능의 Pro 제한 대신 공개 샘플 테스트를 선택했다. API만 public same-repo/허용 작성자로 확장하고 구독은 private를 유지한다. 서버 연결은 인증된 Actions runner 대신 보호 환경의 제한된 SSH worker로 구현한다. 아래 초기 설계/계획은 이 변경과 함께 읽으며 최신 증거는 [검증 상태](../../validation.md)를 따른다.

상태: 2026-11-16 사용자 승인. 이후 독립 리뷰의 실행 식별·설치 자원·보안·평가 완전성 보완을 반영했다. 구현과 실제 PR 검증은 진행 전이다.

새 프로젝트에 맞는 AI 코드 리뷰 체계를 구축하고, 실제 리뷰와 운영 경험을 검증 기준에 반영하도록 돕는 공개 저장소를 만든다. 첫 사용자는 개인 개발자이며, 초기 구축은 실제 PR에서 검증이 작동하고 결과가 기록되는 지점까지 책임진다.

공통 스킬과 템플릿에서 시작하되, 적용 이후에는 각 프로젝트가 자신의 기준·설정·문제집을 소유한다. 평소의 리뷰와 허용된 수정은 자동으로 진행하며, 정책 변경·평가 정답 확정·모델 교체는 사람이 판단한다.

## 1. 합의한 범위

- 이 가이드 저장소는 public으로 운영한다. 초기 자동 리뷰 실행 대상은 사용자가 관리하는 private 저장소다.
- 제공 형태는 구축·점검 스킬, 기본 템플릿, 필요한 실행 도구, 사용·운영 문서다.
- 첫 버전은 두 실행 옵션을 제공한다. **self-hosted 서버의 Codex CLI + ChatGPT 구독 인증**, **GitHub-hosted runner의 Codex GitHub Action + OpenAI API 키 인증** 중 프로젝트 설정 시 선택한다.
- 이번 사용자의 우선 검증 경로는 self-hosted 방식이다. API 방식도 실제 사용 가능한 workflow·설정·운영 문서·검증 범위에 포함한다.
- 실행 환경으로 Hermes를 요구하지 않는다. self-hosted 방식은 서버의 Codex를 직접 실행하며, API 방식은 별도 서버 구축을 요구하지 않는다.
- 자동 수정 기능을 포함한다. 프로젝트별 허용 범위를 설정하고, 최종 자동 머지는 기본적으로 끈다.
- 초기 AI 리뷰는 관찰 모드로 운영한다. 테스트·린트 등 필수 검사는 차단 조건으로 두며, AI 지적의 차단 전환은 평가 근거와 사용자 승인으로 결정한다.
- 첫 종단간 검증은 별도의 private Python 샘플 저장소에서 수행한다.
- 프로젝트의 실제 리뷰 기록·사고 사례·평가 문제집은 해당 private 저장소에 축적한다. 공개 가이드에는 합성 예제와 재사용 가능한 템플릿을 제공한다.
- 7개 방어 계층 전체에 대한 적용 계획을 제공한다. 아직 필요한 환경이나 기능이 없는 계층은 적용 조건과 다음 작업을 남긴다.

첫 버전에는 독립 SaaS, 상시 프로젝트 감시 서비스, 모든 모델 공급자의 실행 연동, 승인 없는 정책 변경, 공개 PR의 구독 인증 실행을 포함하지 않는다. 모델 교체가 가능하도록 평가 데이터와 모델 호출 부분을 분리하되, 첫 모델 실행기는 Codex로 하고 실행 위치·인증이 다른 두 경로를 검증한다.

## 2. 검토한 접근과 선택

| 결정 | 검토한 접근 | 선택과 이유 |
| --- | --- | --- |
| 제공 형태 | 문서·템플릿만 제공 / 프로젝트를 해석하는 스킬 / 전용 CLI 중심 제품 | 스킬과 템플릿을 중심으로 하고 반복 실행에 필요한 작은 도구를 포함한다. 프로젝트 상황에 맞춘 구축과 실제 적용 확인이 필요하다. |
| 프로젝트와 원본의 관계 | 원본을 매 실행 참조 / 설치한 구성을 프로젝트에서 독립 관리 | 프로젝트에 실행에 필요한 구성을 남긴다. 원본의 로컬 경로나 최신 버전에 일상 실행이 종속되지 않는다. |
| GPT 실행 경로 | OpenAI API 키 기반 Action / 기존 서버의 구독 인증 Codex | 두 방식을 프로젝트별 선택 옵션으로 제공한다. 이번 사용자는 self-hosted 경로부터 검증한다. 실행 중 다른 인증·과금 경로로 자동 전환하지 않는다. |
| 수정 범위 | 리뷰만 수행 / 허용 범위 안에서 수정과 재검증 / 자동 머지까지 수행 | 허용 범위 내 수정과 재검증을 포함한다. 민감 영역 변경과 최종 머지는 사람의 판단을 유지한다. |
| 최초 실전 검증 | 기존 제품에 즉시 적용 / 별도 private 샘플에서 검증 | 작은 Python 샘플의 실제 PR로 먼저 검증한다. 정상 사례와 의도적인 버그의 예상 결과를 명확히 정의할 수 있다. |

## 3. 구성과 자료의 소유권

| 위치 | 보관하는 것 | 갱신 방식 |
| --- | --- | --- |
| 공개 가이드 저장소 | 구축·점검 스킬, 공통 기준, 템플릿, 실행·평가 도구, 합성 예제, self-hosted 및 API 방식의 설치·운영 안내 | 공통 기능과 사용 경험을 반영해 버전으로 배포한다. |
| 적용한 private 프로젝트 | 프로젝트별 스킬·리뷰 기준·위험도 정책·실행 명령·계층별 상태·승인된 평가 사례 | 프로젝트 코드와 함께 버전 관리한다. 정책과 문제집 변경에는 사람의 확인을 남긴다. |
| self-hosted 실행 서버 | 구독 방식에서 사용하는 Codex, 인증 상태, runner, 작업별 임시 공간 | 운영 안내에 따라 버전을 고정해 관리한다. 한 프로젝트의 실행 상태가 다른 프로젝트에 섞이지 않도록 한다. |
| GitHub-hosted 실행 환경 | API 방식의 workflow, 버전을 고정한 Action·Codex, 작업별 임시 공간 | GitHub Secrets를 통해 API 키를 연결한다. 프로젝트가 별도 실행 서버나 ChatGPT 로그인 캐시를 유지할 필요는 없다. |
| 실행 기록 저장소 | PR별 실행 결과, 검증 증거, 제한된 보존 기간의 원본 로그 | 승인된 사례만 장기 보관 문제집으로 전환한다. 원본 로그 보존 기간은 설정으로 관리한다. |

공통 템플릿의 출처와 버전을 프로젝트에 기록한다. 같은 구축 스킬을 다시 실행해도 기존 사용자 편집과 프로젝트에서 발전시킨 규칙을 보존한다. 공통 업데이트는 차이와 충돌을 설명하는 변경안으로 제시한다. 한 프로젝트의 개선을 공통 템플릿에 올리는 일은 별도 판단이다.

독립 설치에는 실행 도구뿐 아니라 프롬프트와 입출력 schema 등 실행에 필요한 모든 자원을 포함한다. 원본 checkout을 제거한 상태에서 실제 요청 구성과 모의 모델 실행까지 확인한다.

리뷰 기준, 위험도·수정 정책, 결과 형식, 평가 문제집은 두 실행 경로에서 공통으로 사용한다. 경로별로 다른 부분은 runner·인증·호환성 확인·사용량 수집 등 실행에 필요한 설정으로 한정한다. 실행 경로를 바꿀 때 프로젝트에 축적한 규칙이나 문제집을 다시 만들지 않는다.

이 가이드 자체는 public이므로 구독 인증을 사용하는 PR 검증 workflow의 대상이 되지 않는다. 가이드의 일반 테스트와 private 샘플의 실제 모델 실행 검증을 구분한다.

## 4. 처음 적용하는 과정

1. **현황 파악:** 저장소의 지침, 코드, 테스트·빌드 명령, CI, 배포 여부, 권한 경계, 민감 경로를 확인한다. 찾을 수 있는 사실은 직접 조사하고, 제품 의도와 실패 비용처럼 사람만 정할 수 있는 내용을 질문한다.
2. **초기 기준 작성:** 프로젝트가 지켜야 할 동작과 실패 사례를 리뷰 기준으로 구체화한다. 프로젝트에 아직 없는 기능을 이미 검증하는 것처럼 표시하지 않는다.
3. **적용안 구성:** 실행 방식을 명시적으로 선택하고 프로젝트별 스킬, 실행 명령, 위험도·수정 정책, PR 기록 양식, 계층별 적용 상태를 만든다. 기존 지침 파일에 필요한 진입점을 연결한다.
4. **자동 실행 연결:** private 저장소의 PR 이벤트를 선택한 runner와 Codex 실행 및 결과 수집에 연결한다. self-hosted 방식은 서버·구독 인증을 확인하고, API 방식은 GitHub Secrets·API 모델 접근·실행 예산을 확인한다. 실제 호출에 사용한 기준 파일과 버전을 실행 기록에 남긴다.
5. **동작 검증:** 중요 규칙을 위반하는 사례와 정상 사례를 별도 컨텍스트로 검사한다. 실제 PR에서 리뷰·허용된 수정·테스트·재리뷰·결과 기록을 확인한다.
6. **인수 결과 제시:** 현재 작동하는 항목, 적용 대기 항목, 사용자가 해야 하는 계정·인증 작업, 다음 재점검 조건을 보여 준다.

`AGENTS.md` 등의 작업 지침에는 재점검 조건과 호출 방법을 연결한다. CI에서 필수로 실행해야 하는 동작은 실행 설정으로 연결한다. 단순히 지침에 링크를 넣었다는 이유로 기준이 적용됐다고 판정하지 않는다.

아직 코드나 실행 환경이 없어 실제 PR 검증을 할 수 없으면 준비된 구성과 미검증 항목을 구분해 반환한다. 이 상태는 초기 구축 완료에 해당하지 않는다.

## 5. 7개 계층의 적용과 성장

각 계층에는 현재 상태, 증거, 적용 조건, 다음 작업, 재점검 시점을 기록한다. 예를 들어 `미구성`, `검증 필요`, `작동 확인`, `적용 대기`, `해당 없음`으로 구분한다. 파일이 존재한다는 이유로 `작동 확인`으로 올리지 않는다.

| 계층 | 처음 마련할 것 | 발전하거나 활성화할 조건 |
| --- | --- | --- |
| 1. PR 전 검증 | 실행 가능한 테스트·빌드 명령, 증거 기록, 작성 컨텍스트와 구분된 리뷰 | 코드와 기능이 생길 때 검증 명령과 사례를 보완한다. |
| 2. PR AI 리뷰 | 프로젝트 기준, diff와 의도 전달, 지적 검증, 결과·실행 조건 기록 | 실제 누락·오탐을 바탕으로 기준과 리뷰 강도를 보완한다. |
| 3. 보안 검증 | 일반 버그와 구분된 보안 검토 기준 및 적용 가능한 자동 검사 | 인증·권한·비밀·외부 입력 등의 기능이 생기면 관련 검사를 추가한다. AI 지적의 차단 전환은 별도 승인한다. |
| 4. 필수 CI | 프로젝트에 맞는 테스트·린트·타입 검사·빌드 및 테스트·복구 설명 양식 | 실제 명령 실행과 private 샘플의 머지 차단을 확인한다. |
| 5. 위험도별 사람 확인 | 민감 경로와 변경 특성, 확인이 필요한 조건 | 초기에는 보수적으로 설정하고, 승인 완화는 평가 근거와 사람의 판단으로 진행한다. |
| 6. 통합과 점진적 배포 | 현재 브랜치·통합 방식, 향후 merge queue·기능 플래그·배포 전략의 적용 조건 | 배포 준비 시 실제 서비스 특성과 사용 가능한 플랫폼 기능에 맞춰 활성화한다. |
| 7. 감지와 복구 | 실패 신호, 확인할 사람, 복구 절차와 사례 기록 양식 | 첫 배포 전에 해당 서비스의 감지·복구 방법을 검증한다. 장애는 회귀 검사와 평가 사례로 연결한다. |

1인 프로젝트에서 독립된 사람 두 명의 승인을 구현한 것처럼 표시하지 않는다. 적용 가능한 확인 방식과 남는 한계를 기록한다. 배포 전 프로젝트에도 6·7번의 적용 조건을 남기되 배포 안전성이 검증됐다고 주장하지 않는다.

## 6. PR 실행과 종료 조건

### 6.1 실행 단위

- 한 실행은 저장소, PR, base SHA, head SHA, PR 의도·참고 맥락을 포함한 입력 digest, 정책 버전, 실행 경로·인증 종류, 모델·CLI·프롬프트 버전에 연결한다. API 경로의 Action·runner 버전 등 재현에 필요한 실행 환경도 기록하며 인증 값 자체는 저장하지 않는다. 중복 판단과 결과 복구에도 이 입력 식별자를 사용한다.
- PR마다 작업 공간과 대화 컨텍스트를 분리한다. 작성, 리뷰, 지적 검증의 역할도 컨텍스트를 구분한다.
- 첫 리뷰는 PR 의도와 변경 전체를 관련 코드에 비춰 검토한다. 수정 후에는 변경된 부분과 기존 지적의 해소 여부를 중심으로 재검토한다.
- 이전에 처리한 지적은 이유 없이 다시 제기하지 않는다. 같은 실행이나 이벤트가 반복돼도 댓글·수정 커밋·평가 후보가 중복 생성되지 않도록 한다.
- 새 커밋이 들어오면 오래된 head의 결과를 현재 커밋에 대한 승인이나 통과로 사용하지 않는다. 수정 푸시 전에 예상 head와 실제 head를 확인한다. base나 PR 의도만 바뀌어도 이전 입력의 결과를 재사용하지 않으며, 게시 전에 입력의 유효성을 재확인한다.
- 운영 정책과 실행 도구는 신뢰된 버전에서 읽는다. 평가 중인 PR이 자신의 검증 기준이나 수정 허용 범위를 완화해 적용받을 수 없어야 한다.

### 6.2 리뷰와 위험도

리뷰는 실제 동작 오류, 요구사항 불일치, 보안·데이터·복구 관련 영향을 중심으로 한다. 린트가 처리하는 스타일이나 근거 없는 추측은 지적 대상에서 제외한다. 지적에는 관련 파일·위치, 발생 조건, 영향, 코드나 실행 결과의 근거를 요구한다.

경로·변경 종류 같은 규칙과 AI의 diff 판단을 함께 사용한다. 민감 경로 규칙은 최소 위험도를 정하며 AI 판단으로 낮출 수 없다. 판단 근거가 부족하면 낮은 위험으로 간주하지 않는다. 리뷰 강도와 사람 확인 조건은 프로젝트 설정으로 남긴다.

일반 버그 검토와 보안 검토의 결과를 구분하고, 발견된 지적은 별도 검증 단계를 거친다. 첫 버전에서 대규모 다중 에이전트 투표 체계는 요구하지 않는다.

### 6.3 자동 수정

프로젝트 구축 시 자동 수정의 활성화 여부와 허용 범위를 정한다. 활성화한 범위 안의 일반 코드 변경은 검증된 지적을 바탕으로 PR 브랜치에서 수정하고, 테스트와 별도 재리뷰를 수행한다.

다음 변경은 자동 적용 범위에 넣지 않고 사람 확인을 받는다.

- 인증·권한·결제·데이터 마이그레이션·CI 및 릴리스 설정 등 지정한 민감 영역
- 리뷰 정책, 수정 허용 범위, 평가 문제집의 정답이나 채점 기준 변경
- 지적 해소에 필요한 범위를 벗어난 설계 변경이나 새로운 기능

필요한 회귀 테스트를 추가할 수 있지만, 통과를 위해 기존 검사를 삭제·완화하거나 검증 자체를 건너뛰는 변경은 자동 승인하지 않는다. 민감 영역 승인도 검토한 범위와 커밋에 연결하며 이후의 모든 변경에 대한 포괄 승인으로 사용하지 않는다.

승인의 내용뿐 아니라 출처를 확인한다. 모델이나 worker가 만든 `actor`, `approved` 값은 승인이 아니다. 신뢰된 GitHub 사용자 이벤트 또는 모델 실행과 분리된 운영자 명령에서 승인을 받고, 원본 이벤트·사용자 권한·대상 입력과 패치 digest를 검증한다. 평가 정답 확정과 정책 변경에도 같은 원칙을 적용한다.

반복 횟수에 상한을 둔다. 구현 기본 제안은 **리뷰·수정·재검증 최대 3라운드**이며 프로젝트 설정으로 조정할 수 있다. 같은 실패의 반복, 범위 초과, 사용 한도 소진, 상한 도달 시 미해결 사항과 증거를 남기고 종료한다. 자동 머지는 기본적으로 하지 않는다.

### 6.4 결과 상태

결과는 최소한 `검증 완료`, `지적 있음`, `사람 확인 필요`, `실행 미완료`, `실행 실패`를 구분한다. 인증 실패, 시간 초과, 모델 한도 소진을 지적 없는 성공으로 바꾸지 않는다.

초기 관찰 모드에서는 AI 결과를 참고 정보로 게시한다. AI 결과의 상태와 필수 CI의 통과 상태를 구분한다. 추후 차단 모드에서는 승인된 중요도·미해결 조건을 결정적인 검사로 연결하고, 차단 대상 리뷰가 미완료인 상태를 통과로 처리하지 않는다. 오탐을 해소할 때는 판단 이유를 기록한다.

## 7. 실행 방식과 공개 운영 가이드

### 7.1 프로젝트별 선택

| 항목 | self-hosted 구독 방식 | GitHub-hosted API 방식 |
| --- | --- | --- |
| 실행 위치 | 사용자가 관리하는 서버의 self-hosted runner | GitHub가 제공하는 runner |
| 모델 인증 | Codex의 ChatGPT 구독 인증 | GitHub Secrets에 등록한 OpenAI API 키 |
| 준비할 것 | 서버, Codex, 구독 로그인, runner | API 프로젝트·키·사용 예산, workflow |
| 사용량과 비용 | 구독 사용 한도와 서버 운영 비용 | API 사용량 과금과 해당 계정의 GitHub Actions 사용 조건 |
| 운영 책임 | 서버·runner·CLI·인증 유지 | API 키·사용량 관리와 Action·CLI·workflow 버전 관리 |

API 경로는 공식 `openai/codex-action`을 우선 활용한다. 이 Action은 API 키를 연결해 Codex를 실행하고, 사용할 모델·CLI 버전·sandbox와 결과 파일을 설정할 수 있다. 별도의 OpenAI API 호출 애플리케이션을 새로 만드는 것을 첫 요구사항으로 두지 않는다. [Codex GitHub Action 안내](https://learn.chatgpt.com/docs/github-action)

API 사용량은 ChatGPT 구독과 별도 과금 체계에 속한다. 사용자가 API 방식을 명시적으로 선택하고 키와 실행 예산을 설정한 뒤 호출한다. 구체적인 요금은 설치 시점의 공식 안내를 참조한다. [OpenAI 과금 안내](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)

### 7.2 self-hosted 운영 안내

공개 문서에는 self-hosted 방식의 다음 내용을 포함한다.

1. Linux 서버 준비, 필요한 자원·도구, 실행용 계정과 작업 공간 설정
2. 검증된 Codex 버전 설치·고정과 ChatGPT 구독 로그인
3. private 저장소용 GitHub Actions self-hosted runner 등록·실행·상태 확인
4. 프로젝트 연결, 신뢰할 이벤트·저장소·작성자 제한, 필요한 GitHub 권한 설정
5. 작업별 공간, 동시 실행 제한, 시간·반복·사용량 제한과 결과 보존
6. 인증 만료, 구독 한도 소진, 서버 재시작, 중단된 작업과 오래된 결과 처리
7. CLI·모델 변경 전 호환성 검사와 평가, 실패한 변경의 복구

예시는 서버 주소·계정·경로를 사용자가 채우는 형태로 제공한다. 실제 운영 환경의 접속 정보, 인증 파일, private 프로젝트 자료를 공개 저장소에 넣지 않는다.

설치 단계는 서버에서 할 일, GitHub에서 할 일, 프로젝트에 생성할 구성을 구분한다. 재실행해도 중복 runner나 지침 블록을 만들지 않도록 기존 상태를 확인한다.

### 7.3 API 방식의 설치와 운영 안내

- API 프로젝트와 사용할 모델의 접근 가능 여부, 키 등록, 사용량·과금 확인 방법
- GitHub Secrets 연결, GitHub-hosted runner 선택, 필요한 GitHub 권한 설정
- Action·Codex·모델·프롬프트 버전 고정과 프로젝트 기준 연결
- 실행 시간·반복·토큰 등 지원 가능한 상한, 재시도 제한, 사용량과 확인 가능한 비용 기록
- API 인증 실패, rate limit, 사용 예산 부족, runner 중단 시의 상태 표시와 재실행
- 공통 정상·위반 사례와 자동 수정 흐름을 사용하는 실제 PR 검증

API 호출에 필요한 키는 해당 Action에 연결하고, 저장소 코드를 실행하는 job 전체의 환경 변수로 노출하지 않는다. 모델의 수정 결과 생성, 별도 테스트, GitHub 쓰기 권한을 사용하는 반영 단계를 분리한다. API 방식도 자동 수정과 민감 영역의 확인 정책을 동일하게 적용한다.

### 7.4 공통 실행 경계와 경로 변경

**인증과 실행의 경계:** 리뷰 작업은 private 저장소와 승인된 이벤트에 한정한다. PR의 내용은 명령 권한을 부여하는 지시로 취급하지 않는다. 모델 실행에 필요한 인증과 GitHub에 결과·커밋을 게시할 권한을 분리하며, 프로젝트의 빌드·테스트 프로세스에 해당 자격증명을 전달하지 않는다. 모델 도구와 저장소 코드 실행 환경에서 인증 자료에 접근하지 못하는 구성을 실제로 검증한 뒤 **리뷰·보안 검토·지적 검증·자동 수정을 포함한 모든 PR 입력 기반 모델 실행**을 활성화한다. 실패하면 계층 상태를 `검증 필요`로 남기고 무자격증명 오프라인 검사만 계속한다. `read-only` 옵션만으로 비밀 파일의 읽기 격리까지 보장한다고 설명하지 않는다.

**workflow의 출처:** 권한 있는 진입점은 보호된 ref의 workflow만 사용한다. PR에 추가된 새 workflow/job이 이 검사를 우회해 인증이 있는 runner에 진입하지 못하도록 플랫폼 접근 정책을 검증한다. self-hosted runner는 workflow/ref 접근 제한이 확인된 구성에만 연결한다. 이를 제공할 수 없는 계정에서는 별도 private 제어 저장소로 runner 진입점을 분리하는 설치안을 사용하거나 실행을 보류한다. 제어 저장소를 사용할 때에도 public 가이드 checkout에는 의존하지 않는다. API 키와 dispatch 권한도 PR이 바꾼 workflow에 노출되지 않는 보호된 환경에 둔다.

**자동 발견되는 지침:** 실행 CWD·설정은 신뢰된 영역에 고정한다. PR의 `AGENTS.md`, `AGENTS.override.md`, 프로젝트 스킬·Codex 설정 등은 자동 로드 경로에서 제거하고 원래 경로를 보존한 비활성 자료로 검토한다. 별도 verifier도 같은 경계를 적용한다. 악성 프로젝트 지침이 시작 시 로드되지 않는지 고정 CLI에서 확인한다.

개인 작업 환경의 메모리·스킬·후크를 무조건 CI에 상속하지 않도록 실행 구성을 명시한다. 구체적인 구성 방법과 사용할 플래그는 설치된 CLI에서 검증한다. 구독 한도 소진 시 유료 API 키로 자동 전환하지 않으며, API 실행 실패 시에도 구독 경로나 다른 공급자로 자동 우회하지 않는다.

경로 변경은 프로젝트 설정의 명시적인 변경으로 수행한다. 동일한 리뷰 기준·문제집·결과 형식을 유지하고 호환성과 기본 평가를 다시 확인한다. 두 인증 방식에서 같은 모델을 사용할 수 있는지 먼저 확인하며, 사용할 모델이나 도구가 달라지면 비교 결과에 그 차이를 기록한다. 같은 입력 계약을 사용한다는 이유로 리뷰 품질까지 같다고 가정하지 않는다.

구독 인증 CI 경로는 private 저장소에 한정한다. 이는 API 인증 경로와 구분되는 제약이다. [OpenAI 비대화형 실행 안내](https://learn.chatgpt.com/docs/non-interactive-mode#authenticate-in-automation) 이번 초기 지원·검증 범위는 두 방식 모두 기존 합의대로 private 저장소로 유지한다. 공개 저장소에 API 방식을 적용하는 지원은 공개 PR·fork·작성자·비밀 접근 정책을 정하고 별도로 검증할 때 확장한다.

## 8. 경험 기록과 개선

원본 실행 기록과 승인된 지식을 구분한다. 원본에는 PR·커밋·실행 조건, 최종 지적, 지적 검증 결과, 실제 수정, 실행한 검사와 결과, 사람의 처리 이유를 남긴다. 비밀 값이나 인증 자료를 로그에 저장하지 않는다.

AI는 리뷰 결과, 오탐 판정, 장애·롤백 사례에서 개선 후보를 만든다. 실제 버그인지, 의도된 동작인지, 기계적인 검사로 옮길 수 있는지를 구분한다. 자동 수정이 이루어졌거나 댓글이 닫혔다는 사실만으로 정답이 확정됐다고 간주하지 않는다.

- 실행 가능한 반복 오류는 회귀 테스트·린트·정적 검사로 옮긴다.
- 맥락 판단이 필요한 내용은 프로젝트의 리뷰 기준으로 반영한다.
- 누락과 오탐 사례는 사람이 정답과 근거를 확인한 뒤 문제집에 포함한다.
- 정책·스킬·문제집 변경안에는 근거와 관련 평가 결과를 함께 제시한다.

첫 배포 준비, 인증 기능 도입, 데이터 마이그레이션, 장애 발생, 모델 교체 같은 재점검 조건을 프로젝트 지침에 연결한다. 사용자가 직접 점검 스킬을 호출할 수도 있어야 한다.

## 9. 모델 교체에 사용할 문제집

### 9.1 사례 구성과 재현

각 사례에는 아래 정보를 보관한다.

- 당시 입력: 검토 대상 코드 상태와 diff, PR 의도, 필요한 프로젝트 맥락
- 기대 결과: 찾아야 할 문제와 영향, 지적하지 않아야 할 정상 동작, 정답 확정 근거
- 출처: 원본 PR·커밋·수정·장애 또는 합성 사례라는 구분
- 실행 조건: 프로젝트 규칙, 프롬프트, 도구 접근 범위, 실행 경로·인증 종류, 모델·CLI·Action·설정 버전
- 평가 결과: 발견·누락·오탐·판정 보류, 실행 시간과 확인 가능한 사용량

원본 PR URL만 남기지 않는다. 브랜치 삭제나 코드 변경 이후에도 재실행할 수 있도록 입력 스냅샷 또는 재현에 충분한 fixture와 그 출처를 보관한다.

정답·수정본·채점용 자료는 리뷰어에게 제공하는 입력과 물리적으로 분리한다. 작업 디렉터리, 검색 경로, 접근 가능한 Git 이력에 평가 정답이 섞이지 않도록 한다. 원래 댓글과 문장이 일치하는지를 채점하지 않고, 같은 문제를 올바른 근거로 발견했는지를 평가한다.

정답은 평가 제어·채점 영역에만 두며 모델 worker에는 input만 전달한다. 별도 디렉터리에 복사했다는 사실만으로 격리가 확인되지는 않는다. 실제 모델 도구가 상위 정답 경로·다른 실행 자료·원본 PR에 접근할 수 없는지 검사한다. 평가 시 웹 검색·GitHub 연결·MCP 등 외부 회수 경로를 기본적으로 끄며, 모델 추론 통신만 허용한다.

### 9.2 비교와 교체

기존 모델과 후보 모델을 같은 사례, 같은 규칙·도구·채점 기준으로 실행한다. 버그 탐지 모델이나 지적 검증 모델을 바꿀 때 각 역할의 결과와 최종 게시될 리뷰 결과를 함께 비교한다. 채점 기준과 채점 모델도 버전으로 남기며, 후보를 유리하게 만들기 위해 평가 도중 바꾸지 않는다.

평가 전에 corpus digest와 사례·실행 구성·trial의 전체 기대 목록을 고정한다. 결과 행의 누락·중복·알 수 없는 trial, 미완료 또는 판정 보류가 있으면 비교 전체를 교체 보류로 둔다. 누락된 실행을 완료율의 분모에서 빼지 않는다.

중요 문제의 탐지, 일반 문제의 탐지, 정상 사례의 오탐, 실행 완료율, 시간·사용량을 나누어 보고한다. 평균 점수가 좋아져도 기존에 잡던 중요한 문제를 새로 놓치면 교체를 보류한다. 중요 사례는 반복 실행해 일관성도 확인한다. 구현 기본 제안은 **중요 사례당 3회 비교**다.

자동 채점만으로 판단하기 어려운 지적은 `판정 보류`로 남겨 사람이 확인한다. 채점 자체에 AI를 사용하면 사람에게 확인된 기준 사례로 채점 결과를 보정한다. 평가 결과와 근거를 확인한 사용자가 교체를 결정한다.

처음의 정상·위반 사례 한 쌍은 연결과 기본 동작을 확인하는 자료다. 이 작은 표본만으로 일반적인 동등 성능을 입증했다고 표현하지 않는다. 실제 경험이 쌓이면 튜닝에 사용하는 사례와 교체 판단에 사용하는 고정 평가 사례를 구분하고, 평가 범위와 한계를 함께 보고한다.

모델의 가중치를 자동 학습시키는 기능은 첫 범위에 없다. 발전시키는 대상은 프로젝트의 규칙, 검사, 스킬, 평가 데이터와 실행 구성이다.

## 10. private Python 샘플 검증

작은 Python 프로젝트에 정상 동작과 명확한 버그 사례를 정의하고 실제 PR로 검증한다. 민감 경로의 예제도 두어 자동 수정의 경계를 확인한다. 실제 서비스 데이터나 운영 자격증명은 샘플 입력에 사용하지 않는다.

self-hosted 경로부터 종단간 검증하고, 같은 샘플과 평가 기준으로 API 경로도 검증한다. 각 경로의 결과를 따로 기록한다. API 키·예산이 준비되지 않았으면 구성 검사 결과와 실제 호출 미검증 상태를 구분하며, self-hosted 성공으로 API 실행까지 검증됐다고 표시하지 않는다.

완료 조건은 다음과 같다.

1. 스킬을 적용하면 실행 가능한 구성과 계층별 적용 계획이 생성된다. 재적용해도 사용자 편집을 보존한다.
2. 정상 PR에서는 의도적으로 넣은 오탐 유발 조건을 실제 버그로 보고하지 않는다.
3. 버그 PR에서는 위반 동작과 근거를 지적하고 별도 검증 단계에서 타당성을 확인한다.
4. 허용한 일반 코드의 지적은 PR 브랜치에서 수정되고, 회귀 검사와 별도 재리뷰가 최신 커밋에 대해 수행된다.
5. 민감 경로나 정책·정답 변경은 자동으로 적용되지 않고 사람 확인을 요구한다.
6. 반복 이벤트, 새 커밋 도착, 반복 상한, 시간 초과·인증 실패를 처리하고 미완료를 성공으로 표시하지 않는다.
7. 원본 기록에서 평가 후보를 만들고, 사람이 확인한 사례만 문제집에 포함한다.
8. 같은 입력으로 기존·후보 실행 구성을 비교하고, 중요 문제를 놓치는 후보의 교체를 보류한다.
9. 자동 수정 커밋 이후에도 테스트와 재리뷰가 실제 실행된다. 후속 GitHub 이벤트가 자동으로 발생한다고 가정하지 않는다.
10. 공개 가이드의 설명만으로 선택한 방식에 필요한 서버 또는 API 준비, GitHub·프로젝트 설정, 운영 시 확인할 상태를 파악할 수 있다.
11. 두 실행 경로에서 같은 기준·수정 정책·문제집·결과 형식을 사용하며, 경로 변경 시 프로젝트의 개선 내용을 보존한다.
12. 구독 한도 소진이나 API 인증·예산 오류에서 다른 인증·과금 경로로 자동 전환하지 않는다. 두 옵션의 실사용 지원 완료는 각 경로의 실제 PR 검증을 모두 통과한 뒤 선언한다.

실제 서버 또는 GitHub-hosted runner와 실제 PR을 사용하는 검증, 합성 fixture를 사용하는 도구 테스트, 평가 사례의 품질 검증을 구분해 결과를 기록한다.

## 11. 구현자가 정할 세부사항

다음은 합의한 동작을 바꾸지 않는 범위에서 구현자가 정하고 문서에 근거를 남긴다.

- 스킬과 템플릿의 디렉터리·파일 이름, 실행 명령 이름
- 필요한 작은 실행 도구의 언어와 라이브러리. 기존 도구와 표준 라이브러리를 우선한다.
- 설정·결과·평가 사례의 구체적인 schema와 저장 경로
- GitHub 결과 게시 방식, 수정 커밋 이후 재검증을 확실히 실행하는 방식
- 상태 저장·중복 방지·취소·재시도의 구체적인 구현
- 각 실행 경로에서 인증과 저장소 코드 실행을 분리하는 지원 가능한 구성
- 로그 보존 기간과 실행 시간·동시 실행의 초기 설정값
- 샘플의 버그 종류와 테스트 명령, 한국어를 기본으로 하는 문서 구성

반복 제한과 중요 사례 반복 평가의 제안값은 초기 설정이며 효과를 측정해 조정한다. 실제 private 샘플 저장소의 소유 계정·이름, 선택한 실행 방식에 필요한 서버 접속 정보 또는 API 키 등록·예산 설정은 설치 입력으로 받으며 공개 문서에 고정하지 않는다.

실행 방식의 명시적 선택과 자동 과금 경로 전환 금지, public 가이드와 초기 private 실행 대상의 구분, 민감 영역의 사람 확인, 자동 머지 기본 비활성화, 승인 없는 정책·정답 변경 금지는 구현 편의 때문에 바꾸지 않는다.

## 12. 선행 확인과 근거

설계 과정에서 self-hosted 서버의 Codex를 직접 확인했다. 기존 `0.118.0`에서는 현재 모델 목록의 `max` 추론 수준을 해석하지 못하는 오류와 요청 시간 초과가 관찰됐다. 임시 `0.169.0` 실행 파일에서는 API 키 환경 변수를 제거하고 ChatGPT 인증을 강제한 상태로 `gpt-6-astra` 요청이 약 23초 만에 지정된 응답을 반환했다. 임시 파일은 정리했으며 기본 설치는 교체하지 않았다.

이는 비대화형 모델 호출의 동작 확인이다. GitHub Actions의 실제 PR 연결, 코드 리뷰 정확도, 자동 수정, 인증 격리의 종단간 검증을 대신하지 않는다. `0.169.0`과 해당 모델은 관찰된 조합이며, 모든 이후 버전이나 계정에서의 동작을 보장하는 값이 아니다.

API 경로의 공식 Action과 인증·설정 방식을 문서로 확인했으나, 이 설계 작성 단계에서는 API 호출이나 과금을 발생시키는 검증을 수행하지 않았다.

7개 계층과 사고를 평가 사례로 되돌리는 접근은 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)를 참고했다. 원문의 자동 수정은 작성 에이전트를 포함한 팀 운영 흐름이며, 공개 Code Review 서비스 자체는 커밋을 푸시하지 않는다. [Claude Code Review 동작 범위](https://code.claude.com/docs/en/code-review#what-a-review-can-access)

모델과 실행 환경을 함께 평가하고 반복 실행·사람이 확인한 채점 기준을 사용하는 접근은 [Anthropic의 에이전트 평가 안내](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)를 참고했다. 이 프로젝트의 성공 기준과 자동 수정·승인 정책은 위에 명시한 사용자 합의에 따른다.
